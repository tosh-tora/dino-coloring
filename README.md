# きょうりゅう ぬりえ (dino-coloring)

4歳児向けの恐竜ぬりえ Web アプリ（PWA）。iPad の Safari で開いて「ホーム画面に追加」すると、フルスクリーンのアプリとして使える。

**公開URL: https://tosh-tora.github.io/dino-coloring/**

## iPad で使う（PC 不要）

1. iPad の **Safari** で https://tosh-tora.github.io/dino-coloring/ を開く（初回はネット接続が必要）
2. 画面が表示されたら一度 **リロード**（アプリ本体がオフライン用にキャッシュされる）
3. 共有ボタン → **「ホーム画面に追加」**。以後はホームのアイコンから全画面で起動でき、**機内モード／PC を切っていても動く**
4. 誤操作でアプリの外に出ないようにしたい場合は iPad の **アクセスガイド**（設定 → アクセシビリティ）を併用すると安心

> 仕組み: Service Worker が初回ロード時にアプリ一式をキャッシュするため、2回目以降はオフラインで起動する。iOS がストレージ逼迫でキャッシュを削除した場合のみ、再度ネットに繋いで開き直せば復活する。

## 使い方（開発）

```bash
npm install
npm run dev          # http://localhost:5173 （--host 付きで LAN 内の iPad からも見える）
npm run build        # 型チェック + dist/ に本番ビルド
npm run preview      # 本番ビルドの確認
```

iPad で試す: PC と同じ Wi-Fi に繋ぎ、`npm run dev` 起動時に表示される Network URL（例 `http://192.168.x.x:5173`）を Safari で開く。

共有下絵（`public/custom/`）を追加したときは、次の 2 つを順に走らせて結果もコミットする。

```bash
npm run optimize-art public/custom/shared-xxx.png   # 1024x768 化・白背景の透明化・減色
npm run art-levels                                  # レベルを判定して index.json に焼き込む
```

「うごかす」の主役抽出（`src/cutout.ts`）をいじったときは、全下絵にかけて before / after を
見比べる。

```bash
npm run check-cutouts                # 一覧 + 線画にシルエットを重ねた png（cutout-check.local/）
npm run check-cutouts -- pteranodon  # id に部分一致する下絵だけ
npm run check-cutouts -- --no-png    # 一覧だけ（速い）
```

`optimize-art` を通した png は **透明背景の黒線だけ** になる。アプリはこれをそのまま
表示するので、白背景のままの png をコミットすると塗りが線画に隠れてしまう。すでに
透明化済みの画像を渡した場合は透明化をとばすので、かけ直しても劣化しない。

減色は「線の色は使わないので RGB を黒に潰す」＋パレットPNG化の 2 段。塗りは線の下の
レイヤーから透け、はみだしガード・切り抜き・レベル判定はどれもアルファ（線の濃さ）
だけを見るので、色を捨てても見た目と挙動は変わらない。同梱 47 点で 2.3MB → 1.4MB。

## 機能（v1）

- **ぬりえライブラリー**: 同梱の線画 10 点（恐竜 6 + さかな/おはな/ロケット/ちょうちょ）。塗りかけには 🖍️ バッジが付き、開くと「つづきから / あたらしく」を選べる
- **レベル（★〜★★★）**: 下絵の複雑さから 3 段階を自動判定。カードには出さず（絵が隠れないよう）絞り込みチップのみ。子どもは ★ チップで絞り込め（分類チップと併用可）、大人は「ぬりえのかんり」で 1 点ずつ変更、「ぬりえのせってい」で見せるレベル自体を制限できる
- **ブラシ塗り**: 基本 12 色 + じぶんの色（カラーピッカー）+ 消しゴム、太さ 4 段階の大ボタン
- **ぬり方モード**: 🖍️ くれよん（不透明）↔ えのぐ（水彩、下の色と混ざる）↔ 🪣 バケツ。ボタンを押すたびに切り替わり、押した瞬間に「くれよん / えのぐ / バケツ」と一瞬ポップアップする
- **バケツ（ぬりつぶし）**: タップした閉領域を一発で塗りつぶす。**おとなメニューの「ぬりえのせってい」で有効にしたときだけ**モード切替に現れる（既定はオフ）。消しゴムと組み合わせると領域まるごと消せる
- **輪郭線は常に前面**: 線画レイヤーを塗りレイヤーの上に重ねた 2 canvas 構成なので、構造的に塗りつぶせない
- **むしめがね**: 🔍 を押して紙をタップすると、その場所を中心に 2 倍に拡大して塗れる。細かい塗り分けのある ★3 の下絵向け。もう一度押すと元の大きさに戻る
- **もとに戻す**: 1 ストロークずつ Undo（最大 12 段）
- **ぜんぶ消す**: 誤タップ防止のため 1.5 秒長押しで発動（進捗リング表示）。消した直後は Undo で戻せる
- **自動保存**: ストロークごとに IndexedDB へ保存（1.5s debounce）。リロードしても続きから
- **できた！**: 紙吹雪 + ファンファーレ（WebAudio 合成、音声ファイル不要）→ ギャラリーに保存
- **うごかす**: 完成した絵から生き物だけを自動で切り抜き、背景の上で動かす。ボタンを押すまでは完成画像のまま静止し、動いている間にタップすると鳴く。**生き物によって動きと鳴き声が変わる**（はねる＋ガオー / およぐ＋ぽちゃん / とぶ＋キーッ）。鳴き声の高さはシルエットの大きさで決まり、大きい恐竜ほど低い
- **ギャラリー**: 完成作品の一覧。長押しで削除（おとな向け操作）
- **さくひんの ほぞん**（おとなメニュー）: 完成作品をえらんで iPad の写真アプリ／ファイルへ書き出す。共有シート（Web Share）経由で、一度に最大 20 枚
- **下絵メーカー**（おとなメニュー）: 日本語の主題から画像生成AI向けの英語プロンプトを作る「言葉から」モードに加え、手持ちの画像を線画化させる「画像から」モードもある（元画像への忠実さを3段階で指定）。生成したプロンプトは、画像生成AIに元画像を添付したうえで渡す。できた線画は画像アップロードでライブラリーに追加できる。**アップロードした画像は取り込み時に自動で圧縮される**（原本は保存せず、1024×768・透明背景の黒線だけの png にしてから保存する）ので、生成AIが吐いた数MBの画像をそのまま入れてよい
- **PWA**: manifest + Service Worker（cache-first）。一度読み込めばオフラインで動作

## 構成

```
index.html               エントリ（iPad Safari 向け meta 含む）
public/manifest.webmanifest, sw.js, icons/
src/main.ts              画面遷移（ライブラリー/ぬりえ/ギャラリー）
src/paint.ts             ブラシエンジン・Undo（ストロークバッファ方式）・はみだしガード・バケツ
src/tools.ts             ツールバー UI・長押しヘルパー・道具のアイコン（自作 SVG）
src/store.ts             IndexedDB 永続化（works / gallery）
src/lineart.ts           線画カタログ（SVG を ?raw インポート）
src/celebrate.ts         紙吹雪 + WebAudio 効果音
src/level-core.ts        レベル判定の中核（DOM 非依存。ブラウザと CLI で共有）
src/level.ts             レベルのブラウザ側（canvas から読む・キャッシュ）
src/cutout.ts            下絵から主役（生き物）のシルエットを抽出（DOM 非依存の純関数）
src/subject.ts           cutout の DOM / キャッシュ連携・完成画像の切り抜き
src/animate.ts           切り抜いた主役を動かす画面
src/export.ts            完成作品の書き出し（Web Share / ダウンロード）
assets/lineart/*.svg     線画（viewBox 1024x768、透明背景、太い黒線）
```

`navigator.share()` はタップと同じタスクで呼ぶ必要があり、`await` を挟むと iPad Safari に
`NotAllowedError` で弾かれる。そのため `src/export.ts` は data URL → File の変換を `atob` で
完全に同期にしている。一度に共有できる枚数も 20 枚に制限（`SHARE_BATCH_MAX`）していて、超えた
ぶんは選択を残したまま次のタップで送る。なお `npm run dev` を非 https（LAN IP）で開いた場合は
secure context ではないため `navigator.share` 自体が存在せず、ダウンロードのフォールバックに
なる（本番の共有シート経路とは別の動きになる点に注意）。

### 設計メモ

- 塗りレイヤー（下）と線画レイヤー（上、`pointer-events: none`）の 2 canvas。塗りは下にしか乗らない
- ストローク描画は毎フレーム「ストローク全体を一時バッファに描き直して合成」する方式。multiply モードでもセグメント継ぎ目が濃くならない
- 線画 SVG は透明背景・黒線のみ（白背景を入れると塗りが隠れる）
- **バケツ（ぬりつぶし）は、はみだしガードの資産をそのまま再利用している**。ガードは「ストローク開始点を含む閉領域」を線画から作った barrier 上で 4 近傍フラッドフィルして塗り許可マスクにする仕組みで、バケツに必要な処理と同じ。`PaintEngine.fillRegion()` はそのマスクをそのままベタ塗りのクリップに使う（`buildRegionMask()` を `beginMask()` と共有）。フラッドフィルは線の画素へ深さ `LINE_OVERLAP`(20px) まで潜り込むが線を突き抜けないので、**線の下まで塗り込まれて白い隙間が出ず、隣の領域にも漏れない**。線画は前面の別 canvas なので、線の下の塗りは見えない
- バケツは「塗り方」ではなく「道具」なので、`PaintMode`（normal / mix / erase）を広げず独立した `fillTool` フラグにした。消しゴムと直交するため、バケツ + 消しゴム = 領域まるごと消しが自然に出る。はみだしガードの閾値が 0（オフ）でもバケツは効く
- 塗りの合成は `compositeStroke()` に集約してある。なぞり描きとバケツで えのぐ（水彩混色）の扱いが食い違わないようにするため、モード分岐をここ以外に書かないこと
- **バケツは既定でオフ**（`dino-coloring:fill-tool`）。一発で埋まるのは塗り絵の体験として強すぎるので、おとなが明示的に有効化したときだけツールバーに出す。はみだしガードと同じく、**ぬりえ画面に入るときに 1 回だけ読む**（画面を開き直すまで反映されない）
- マルチタッチは最初の 1 本のみ受け付け（簡易パーム対策）
- **むしめがねの拡大は `.stage-inner` への CSS transform だけで行う**。`PaintEngine.toCanvasPos()` は canvas の `getBoundingClientRect()`（＝祖先の transform が反映された矩形）を基準にしているので、塗り側のコードを 1 行も変えずに指の位置と線が合う。canvas の実体は等倍のままなので、はみだしガード・バケツ・もどす・「できた！」の合成もそのまま効く。canvas を実際に拡大する実装に書き換えないこと。拡大の中心はタップした点なので紙の外の余白は見えず、はみ出しを抑えるクランプ計算も要らない。場所選びの間だけ紙の前面に `.zoom-pick` を置き、そのタップが塗りレイヤーに届かないようにしている。パン（2 本指ドラッグ）は入れていない — 最初の 1 本しか受け付けない設計と噛み合わず、4歳に教えるコストに見合わないため
- 「うごかす」の主役抽出は「主役＝太い輪郭線 / 背景＝細い線」という下絵の描き分けを利用する。モルフォロジー演算の半径を総当たりし、シルエットの縁が太線に乗っている割合（confidence）が最大の組み合わせを採用。結果は下絵 id ごとに IndexedDB へキャッシュする（`cutouts`）
- **細いくびれで切り分けたあとは、シルエットの画素を「いちばん近いかたまり」へ割り当て直して戻す**（`severThinBridges`）。触れているだけの雲や草を落とすために開く（収縮）必要があるが、膨張で戻すとくびれより細い先端 — くちばし・翼・とさかの先 — が届かず永久に欠ける（プテラノドンのくちばしと翼の先が動かない不具合）。シルエットの内側だけを通る距離で塗り分ければ、先端は本体に、背景は自分のかたまりに付く。戻せるのは `SEVER_REACH`(60px) 先まで — 先端は本体からせいぜいそのくらいしか離れないが、地面や氷の稜線のような「細いまま画面を横切る線」は数百 px 伸びるので、そこで打ち切って背景として捨てる
- **同じくらいきれいに切れている候補どうしは、面積の大小ではなく「増減した領域が体か背景か」で選ぶ**（`dropsOnlyBackground` / `addsOnlyBody`）。小さくなるのは背景を手放したときだけ、大きくなるのは欠けていた体が戻ってきたときだけ認める。輪郭に切れ目があると塗りがそこから漏れ、翼や胴が丸ごとシルエットの外に落ちるため（プテラノドンが半身だけ動く・マンモスが顔だけ動く不具合）、大きいほうへ乗り換える道が要る
- **ただし大きくなる側は原理的に背景と区別しきれない**。岩・氷・草が生き物と同じ太さで描かれた絵では「増えたぶんも線で囲まれている」が普通に成り立つ。手前の翼（縁一致率 0.994 / 全体の一致率の落ち -0.0019）と背景のシダ（0.996 / -0.0025）は数値上まったく同じなので、`GROW_BODY_COVERAGE` と `GROW_SCORE_DROP` で「増えたぶんがほぼ完全に線で囲まれていて、全体の一致率もほとんど落ちない」ときだけ通す妥協にしてある。この結果、**トリケラトプス（火山）はシダを、パキケファロサウルス（対決）は木を主役と一緒に動かす**（承知のうえの副作用）。しきい値を動かすときは `npm run check-cutouts` で全点を見比べること
- **線だけで中身が無い部品はシルエットに入らない**。ヘラクレスオオカブトの地面より下の足先や触角の先、プテラノドンの脚と足指は、閉じた区画にならないので塗りつぶし方式では拾えない。マスクをインク伝いに広げて拾う実装も試したが、脚が地面の線に触れている絵では地面の線ごと引きずるため使えなかった
- **うごかす の動きは「はねる / およぐ / とぶ」の 3 種類**（`src/animate.ts` の `MOTION`）。種類は `motionOf()` が「下絵 id の明示リスト → カテゴリー(`cat-sea`) → 既定のはねる」の順で決める。とぶ・およぐは絵そのものの性質なので、大人が変えられる分類より id を先に見る。メガロドンのように「ぜつめつどうぶつ」に分類された泳ぐ生き物はカテゴリーでは拾えないため id 側に書く。表に無い下絵（アップロード画像を含む）は従来どおり はねる
- 変形の支点は はねる時だけ足もと。着地で潰れる動きは足もとが軸でないと不自然になる一方、浮いている生き物を足もと基準でかたむけると回転が大げさになるため、およぐ・とぶ はシルエットの中心を支点にする。かたむきは最大でも約 6° なので、タップの当たり判定には持ち込まない（外接矩形のまま）
- 主役と背景の線幅が同じ絵は原理的に分離できない。confidence が低い下絵では演出を出さず、そのままギャラリーへ進む。`src/subject.ts` の `CUTOUT_VERSION` を上げるとキャッシュが作り直される
- **左右で完結していない（画面の外へ切れている）生き物は動かさない**。対決の絵などでは恐竜が画面いっぱいに描かれ、しっぽや胴が左右の外へ出ていることがある。切れた生き物の内側は画像の縁と地続きなので輪郭の内側を塗る方式ではシルエットにならず、代わりに背びれのような「体の一部」だけが閉じた領域として残る（スピノサウルス vs ティラノサウルスでは背びれだけが 9% の主役として採用されていた）。それを動かすと体の一部が本体から剥がれて跳ねてしまうので、この絵では演出そのものを出さない。判定は 2 つ: シルエットが左右の縁に触れていたら不採用（足が下の縁に着くのは普通なので上下は見ない）、そして「輪郭で仕切った紙の区画のうち、画像の一辺だけ・それも左右どちらかに接しているもの」が切り抜けた主役より大きければ、本当の主役は画面の外にいるとみなして空を返す。空や地面は画面の外へ流れ出ていくので複数の辺にまたがり（水面のような横帯は左右の両方に接する）、この条件には当たらない
- **レベルは下絵を追加したときに 1 回だけ判定し、値を焼き込む**。下絵が同じならレベルも同じなので、端末ごとに実行時判定する必要がない。共有下絵は `npm run art-levels` で `public/custom/index.json` に、組み込み SVG は `src/lineart.ts` の `BUILTIN_LEVEL` に、アップロード画像は取り込み時に判定して IndexedDB の `templates` に持つ。同梱 67 点の実行時計算はゼロ。焼き込みが無い下絵（この仕組みより前にアップロードされたもの）だけ実行時に判定して `levels` にキャッシュする
- 判定アルゴリズムは `src/level-core.ts` に集約し、ブラウザと CLI が同じコードを使う。しきい値を 2 箇所に書くとずれるため複製しないこと。`npm run art-levels -- --check` で書き換えずに差分だけ確認できる
- 判定は下絵を 1024x768 → 256x192 に縮小したアルファだけを見る軽い方法。4歳児にとっての難しさは線の"数"ではなく次の 2 つで決まる、という見立てで測り、**難しい方**を採る
  - **細い線の量**: 縮小すると太い線は濃いまま残り、羽根・毛・草・ハッチングのような細い線は薄くなる。「薄いのに 濃い線の隣ではない」画素だけを数えれば、太線のアンチエイリアスと区別して細い線だけを拾える（組み込み SVG は 0、素朴な共有下絵 0.1〜1.5、羽根やハッチングのある下絵 2.7〜13）
  - **小さい領域の広さ**: 塗れる面積のうち小さな区画（画面の 1% 未満）が占める割合。うろこ・翅のような細かい塗り分けほど大きい（素朴な下絵 0〜15%、細かい絵 21〜31%）
- 領域の"数"は使わない。大きな葉が並ぶだけの素朴な絵（ヴェロキラプトル）が難しい側に、細い線だらけの絵（フクイベナートル）が簡単側に落ちてしまうため。しきい値は同梱の下絵の実測と目視ラベルから決めており、67 点が 26/15/26 に分かれる。実行時判定が要る下絵だけ `levels` にキャッシュし、`src/level.ts` の `LEVEL_VERSION` を上げると作り直される
- **縮小はブラウザ任せにしない**。等倍で描いてから 4x4 の面積平均を自前で行う。`drawImage` の縮小フィルターの品質は仕様で決まっておらず、Chrome は面積平均するが WebKit（iPad / Safari）は安価な間引きで済ませる。細い線の量はアンチエイリアスされた薄い画素だけを見る指標なので間引きで真っ先に消え、iPad では ★3 がほぼ消えて大半が ★1 になっていた（fine が 15.5 → 0.1 まで落ちる下絵もあった）。例外は出ないので「もっともらしい ★1」として黙って壊れる
- 大人の手動レベルは `artmeta` 側（名前・分類の上書きと同じ仕組み）。自動判定より常に優先し、「じどう」に戻せる
- **共有下絵の白→透明化もビルド時に焼き込む**（レベルと同じ考え方）。以前はブラウザが起動のたびに 47 枚を 1 枚ずつ読み込み、全画素を走査して透明化し、`toDataURL` で PNG に再エンコードしていた。最初のカードが出るまで 988ms（ローカル実測。iPad はさらに遅い）かかり、13.6MB の data URL を抱えていた。`scripts/optimize-shared-art.mjs` で 1 回やってコミットすることで実行時の画像処理はゼロになり、白背景が一様な透明画素になるぶん png 自体も 5.1MB → 2.3MB に縮んだ。変換規則は `src/level-core.ts` の `lineAlpha` に集約してあり、CLI とブラウザ（アップロード画像）で同じ
- 下絵の png は中身だけ差し替わってファイル名は変わらないため、差し替えたら `public/sw.js` の `CACHE_NAME` を上げること（cache-first なので古い白背景の png が残る）
- ライブラリーは**枠を先に描いてから中身を差し込む**。一覧を待ってから描くとタイトルすら出ない白画面になり、反応していないように見えるため。カード画像は `loading="lazy"` にして、表示のあと `warmSharedArts()` が裏で全部取りにいく（開いていない下絵もオフラインで出せるように）
- 手持ち画像のぬりえ化はアプリ内では行わない（輪郭抽出の精度が実用に足りず断念）。代わりに下絵メーカーで「画像に忠実な線画にして」という英語プロンプトを作り、外部の画像生成AIに元画像を添付して渡してもらう方式にした（`src/template.ts` の `buildColoringPrompt` / `PromptMode`）

## デプロイ

`master` に push すると GitHub Actions（`.github/workflows/deploy.yml`）が `npm run build` して GitHub Pages に自動公開する。`vite.config.ts` の `base: "./"` によりサブパス（`/dino-coloring/`）配下でも動く。

初回セットアップ済みの内容:
- リポジトリ: https://github.com/tosh-tora/dino-coloring
- Pages ソース: GitHub Actions（`gh api --method POST repos/OWNER/REPO/pages -f build_type=workflow` で設定済み）

アプリを更新したら、SW のキャッシュ名（`public/sw.js` の `CACHE_NAME`）を上げると端末側の更新反映が確実になる。
